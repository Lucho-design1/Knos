How we verify

Everything on the app is checkable without trusting this server. This page says what checks each claim, and where.

The demand decision

Qloo's taste API is the only demand oracle. Every number in a report names the call that produced it (endpoint, input, output summary) and each step says how it changed the decision. The verdict and the campaign (who, where, price tier, target, reserve) are computed by published rules — check.RULES, documented in DEMAND_CHECK.md — never by a language model. Without a Qloo key the server answers "cannot decide: no Qloo evidence" and nothing opens. A report is directional demand evidence, not a sales forecast; every Qloo figure is aggregate taste, not a prediction about one person.

The money

Pre-orders are knos_pay escrow orders on Solana devnet (test units of this app's own test mint; no real money). A stage is released only by 2-of-3 referee signatures that the program checks on chain; the referee keys are held by this one server and every commitment says so (UNLISTED PANEL). A released or refunded order's account is closed, so a second release is refused by the chain itself. Deadlines refund to the buyer; anyone may send the refund. Fees come from config/fees.yaml: Knos takes the payout fee only on money released on proof.

Programs: knos_pay test build FaMHCjzyUexFncZrmNyFQNz3gBdsLbhTLke7QBFykJY4 (devnet). Every receipt links its transactions on explorer.solana.com.

The evidence

A milestone's evidence is a public https page that must contain the commitment's claim id. The server fetches it (public addresses only, no redirects, size and time limits) and the referees sign over one canonical pin: knos.ideas.commit.review_evidence, the sha256 of the signed evidence structure, which includes the page's own sha256. The receipt shows both values, and the pin is what the release transaction carries.

The record

Every decision, lock and release is appended to the Knos Record (a hash-chained journal with Sibyl as the agents' working memory beside it), and the record's Merkle root can be anchored on devnet in a Memo transaction signed by the app's test wallet.

The identity

Passkeys: the server keeps only the passkey's public key; your identity is derived from it, and sign-in is an ES256 signature over a fresh challenge checked server-side. There is no seed phrase to lose. The same passkey is your wallet: a LazorKit smart wallet on devnet (program FLb7fyAtkfA4TSa2uYcAT8QKHd2pkoMHgmqfnXFXo7ao) whose one owner is the passkey's P-256 key. A pre-order, a sale of a receivable, a lender's advance and its collection are each signed by the person's passkey and checked on chain by Solana's secp256r1 precompile; the server only pays the fee and relays. No server key buys for anyone. Wallet pre-orders (Blinks) are signed by your own wallet; the server never sees the key.
